MoviePalace — Backend

Database Schema Reference

Three tables manage all persistent state. Movie caches TMDB-sourced film data so the API doesn't call out for every request. Question stores pre-built puzzle records of several types. QuestionMovie is the join table linking them in a many-to-many relationship.

Entity Relationship Diagram

A Question links to multiple Movies via the payload field. A Movie can appear across multiple Questions. QuestionMovie holds exactly these joins and nothing else.

Table Definitions
Movie Cached TMDB film data — fetched once, reused across questions
Field Type Null Source / Description
idPK Int NOT NULL TMDB's own movie ID — used as the primary key so no mapping table is needed
title String NOT NULL /3/movie/{id} → title
releaseDate String? nullable ISO date string (e.g. 1993-06-11)  /3/movie/{id} → release_date
posterPath String? nullable Raw TMDB path segment, e.g. /abc123.jpg. Prepend https://image.tmdb.org/t/p/w500 to construct a full URL.  /3/movie/{id} → poster_path
overview String? nullable Plot synopsis  /3/movie/{id} → overview
keywords String? nullable JSON array of keyword name strings, e.g. ["island","dinosaur","survival"]. Populated by db:sync-keywords.  /3/movie/{id}/keywords → keywords[].name
fetchedAt DateTime NOT NULL Server timestamp set on insert — useful for cache-staleness checks
Question Pre-built puzzle records, one row per playable quiz item
Field Type Null Description
idPK Int NOT NULL Auto-incrementing surrogate key
type String NOT NULL Question category — determines how the client renders it and how the payload is parsed. Values: cast_links · shared_actor · movie_detail
difficulty String NOT NULL Enforced to one of easy · medium · hard at the API layer
payload String NOT NULL JSON blob — structure varies by type. See payload formats below.
createdAt DateTime NOT NULL Server timestamp set on insert

Question Payload Formats

The payload column is a JSON string whose shape depends on the type field.

cast_links A 7-film chain where the player guesses the connecting actor at each step 
{
  "puzzle_number": 1,
  "chain": [
    { "pos": 1, "film": "Jurassic Park",  "tmdb_id": 329  },
    { "pos": 2, "film": "Pulp Fiction",   "tmdb_id": 680  },
    ... 5 more films ...
  ],
  "links": [
    { "from_pos": 1, "to_pos": 2, "intended_actor": "Samuel L. Jackson" },
    ... 5 more links ...
  ]
}
shared_actor Player names an actor who appeared in both films 
{
  "question": "Which actor appeared in both Butch Cassidy and the Sundance Kid and Donnie Darko?"
}
movie_detail A factual question about a single film 
{
  "question": "What year was Inception released?"
}
QuestionMovie Join table — no surrogate id, composite primary key only
Field Type Null Description
questionIdFKPK Int NOT NULL References Question.id
movieIdFKPK Int NOT NULL References Movie.id (the TMDB movie ID)

The composite primary key @@id([questionId, movieId]) enforces uniqueness at the database level — the same film cannot be linked to the same question twice. No auto-increment column is needed because the pair is the identity.

TMDB API Data Sources

All movie data originates from the TMDB API. Four endpoints are used. Three populate the Movie table; the fourth is called live by the /v1/movies/:id/credits route and is never stored.

GET /3/search/movie?query={title}&year={year}

Title → TMDB ID resolution. Used by the sync scripts during seeding to find the canonical ID for a film name. The result's id is then passed to the detail endpoints below. Not stored directly.

lookup only — not stored
GET /3/movie/{id}

Primary movie detail fetch. Populates the core Movie row on first insert.

Movie.id Movie.title Movie.releaseDate Movie.posterPath Movie.overview
GET /3/movie/{id}/keywords

Returns keywords[].name — a flat list of string tags describing the film's themes. Stored as a JSON array in Movie.keywords. Refreshed by running npm run db:sync-keywords.

Movie.keywords
GET /3/movie/{id}/credits

Cast and crew for a film. Returned live by the /v1/movies/:id/credits API route — not stored in the database. Also used by the /v1/movies/overlap route to find shared cast between two films.

live only — not stored
